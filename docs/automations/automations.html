TokenRadar Automations & Ops

This document is the practical runbook for the scheduled automation layer in this repository. It is the canonical automation reference now that the root AUTOMATIONS.md source has been retired.

Automation Inventory

The repository currently has eight GitHub Actions workflows:

  • .github/workflows/social-automations.yml Purpose: route scheduled and manual social publishing slots across Telegram, X, Instagram, Threads, YouTube Shorts, and TikTok. Schedule: 8 platform-aware social slots per day/week, plus manual workflow_dispatch inputs for individual routes, d1-smoke, and all.
  • .github/workflows/daily-content-generation.yml Purpose: generate Smart Drip queue content, quality-gate it, publish a bounded batch, repair formatting, validate, build-gate, commit, and call deploy. Schedule: 06:00 UTC daily, plus manual dispatch.
  • .github/workflows/daily-refresh.yml Purpose: refresh market data, discover TGEs, fetch references, compute metrics, refresh Meta tokens, regenerate OG/sitemap/data artifacts, export analytics baseline, send the system report, commit, and call deploy. Schedule: 17:45 UTC daily, plus manual dispatch.
  • .github/workflows/deploy.yml Purpose: build and deploy the static Next.js export to Cloudflare Pages with typecheck, lint, tests, output verification, file-budget checks, IndexNow ping, diagnostics, and failure alerts. Triggers: push to main, manual dispatch, and reusable workflow_call.
  • .github/workflows/video-assets-refresh.yml Purpose: refresh the persistent b-roll library by hydrating the R2 manifest, fetching provider clips, generating optional Blender loops, and syncing assets back to R2. Schedule: 04:30 UTC Sunday, plus manual dispatch.
  • .github/workflows/performance.yml Purpose: run Lighthouse CI against the static export, upload Lighthouse reports, and run live PageSpeed snapshots outside pull requests when PAGESPEED_API_KEY is configured. Triggers: relevant pull requests, 08:40 UTC Monday, plus manual dispatch.
  • .github/workflows/dependency-security.yml Purpose: run production dependency audit with npm run audit:prod. Triggers: dependency/workflow pull requests, 08:20 UTC Monday, plus manual dispatch.
  • .github/workflows/monthly-data-snapshot.yml Purpose: archive public data, content, and media into a monthly GitHub Release while excluding runtime caches, logs, quarantine, and social cooldown state. Schedule: 23:30 UTC on the 1st day of each month, plus manual dispatch.

Social Workflow

The main social workflow is .github/workflows/social-automations.yml.

It runs platform-aware slots and routes each slot to the correct script:

  • 00:00 UTC daily: Telegram market brief
  • 00:05 UTC Sun/Tue/Thu: Instagram Daily Movers carousel
  • 03:00 UTC daily: X market update
  • 12:00 UTC daily: X interactive poll + one link reply
  • 15:00 UTC daily: Telegram daily poll + X market update
  • 16:00 UTC Tue/Thu: Threads text-native signal
  • 18:00 UTC Mon/Wed/Fri: Short-form video package (Remotion -> R2 staging where needed -> Instagram Reel, Threads video, YouTube Shorts, TikTok)
  • 21:00 UTC daily: Telegram top movers card + X market update

Exclusive slots suppress the standard Telegram market update so polls, movers cards, and video posts do not collide with the regular cadence. The short-form video route uses --platform shorts, so it targets short-form platforms without adding extra Telegram or X posts.

The workflow has its own social-automations concurrency group so social posting is not blocked behind content-refresh jobs. Social cooldown state is restored from and saved back to GitHub Actions cache under data/posted and data/posted_video; it is not committed back to main.

Social Tracking and Ops Ledger

Social runs have a best-effort D1 operations layer before and after publishing:

  • apply D1 ops ledger migrations
  • record automation run started/finished with the current schedule slot or manual input
  • clean expired R2 staging objects that are tracked in D1
  • backfill the social ledger from file-based trackers
  • record Cloudflare/D1/R2 usage snapshots
  • support a manual d1-smoke route and report the ops ledger when that route is selected

These steps are intentionally continue-on-error where possible. They should improve observability without blocking social posting when the ledger is unavailable.

On social failure, the workflow uploads short-retention diagnostics including logs, social trackers, CoinGecko counter state, Remotion props, and generated MP4s.

Content and Refresh Workflows

There are two authored content/data workflows that can push generated artifacts back to main:

  • .github/workflows/daily-refresh.yml Flow: fetch token data, discover upcoming TGEs, fetch reference articles, compute metrics, refresh Meta access tokens, regenerate OG images, consolidate data, validate content, generate sitemaps, commit changed data artifacts with [skip ci], export the engagement analytics baseline, send the system report, and call deploy when data changed.
  • .github/workflows/daily-content-generation.yml Flow: require main, generate Smart Drip queued content, run the queued-content quality gate with auto-fix/delete-failures, publish up to the configured queue limit, inject semantic internal links, repair published article formatting, validate published content, run the production build gate, commit changed content/data artifacts with [skip ci], and call deploy when articles changed.

Both workflows share the git-push-main concurrency group and compare the remote main SHA before pushing. If main changes during generation, they abort instead of auto-merging generated output.

Deploy Workflow

Deployment is handled by .github/workflows/deploy.yml.

The deploy workflow can run from a push to main, a manual dispatch, or a reusable workflow call. Manual deploys are limited to main; reusable callers may deploy a full commit SHA only when allow_sha_ref is true.

Deploy runs these gates before publishing:

  1. validate the requested deploy ref
  2. install dependencies
  3. run npx tsc --noEmit
  4. run npm run lint
  5. run npm run test
  6. run npm run build
  7. verify out/ exists and run npm run deploy:check-files
  8. upload out/ to Cloudflare Pages with wrangler pages deploy
  9. ping IndexNow when INDEXNOW_KEY is configured

Deploy failures upload short-retention diagnostics and send a Telegram report-chat alert when reporting secrets are configured.

Video Assets and Media Staging

Short-form video uses a 15-format editorial rotation with a 14-day format cooldown per platform. Each requested video platform gets its own rendered MP4, editorial format, and visual recipe in the same run. The recipe varies scene order, layout, chart pack, background system, motion pack, color theme, and pacing while preserving the fast TokenRadar tone.

Selected platform formats, recipes, hook, thesis, music track, and visuals are stored in data/posted_video/YYYY-MM-DD/daily-video.json so retries keep the same creative package instead of drifting.

The persistent b-roll library is maintained by .github/workflows/video-assets-refresh.yml:

  • hydrate the current R2 manifest
  • fetch provider b-roll from Pexels/Pixabay when credentials exist
  • generate optional Blender motion loops
  • sync the refreshed manifest and reusable clips to R2

Meta publishing uses a Cloudflare R2 bucket, typically tokenradar-media-staging, to host generated media temporarily. Videos use the video/YYYY-MM-DD/ prefix and Instagram carousel images use ig-carousel/YYYY-MM-DD/. Successful publishes delete their exact staged keys after Meta accepts the media, while failed runs intentionally leave files in place for short-term diagnostics.

Configure the R2 bucket on Standard storage with lifecycle expiration for video/ and ig-carousel/ prefixes after 1-2 days:

  • npx wrangler r2 bucket lifecycle add <BUCKET_NAME> expire-video-staging video/ --expire-days 2
  • npx wrangler r2 bucket lifecycle add <BUCKET_NAME> expire-carousel-staging ig-carousel/ --expire-days 2

Credential and Token Rotation

X posting uses OAuth 2.0 refresh tokens with rotation:

  • active scripts refresh the access token at runtime
  • when X returns a new refresh token, src/lib/x-client.ts writes it to GITHUB_ENV
  • the social workflow persists that rotated token back into the X_OAUTH2_REFRESH_TOKEN GitHub secret with GH_PAT

Because X refresh tokens are single-use, X posting is treated as a serialized concern inside the social workflow/job path.

Meta (Instagram/Threads) uses Long-Lived Access Tokens:

  • scripts/refresh-meta-tokens.ts runs daily via daily-refresh.yml
  • the social workflow can also persist newly returned Instagram or Threads tokens when publish-time rotation occurs
  • updated tokens are pushed to GitHub secrets with GH_PAT

YouTube Shorts uses YOUTUBE_CLIENT_ID, YOUTUBE_CLIENT_SECRET, and YOUTUBE_REFRESH_TOKEN. If the refresh token becomes invalid, regenerate it with scripts/generate-youtube-token.ts.

TikTok uses TIKTOK_ENV to select delivery mode. In sandbox, the script uploads to the authorized creator inbox and sends the publish id plus copy-ready caption to the Telegram report chat. In production, it uses direct video.publish when approved credentials and privacy settings are available. If TikTok API credentials are missing, the video package falls back to Telegram report-chat delivery for manual posting.

Telegram, Alerts, and Diagnostics

There are two Telegram roles:

  • TELEGRAM_BOT_TOKEN + TELEGRAM_CHANNEL_ID Purpose: public channel posting.
  • TELEGRAM_REPORT_BOT_TOKEN + TELEGRAM_REPORT_CHAT_ID Purpose: operational alerts, daily reports, and manual/social fallback packages.

Failure reporting happens in two layers:

  • script-level logging via src/lib/reporter.ts
  • workflow-level fallback alerts in GitHub Actions

Workflows also upload short-retention diagnostic artifacts on failure:

  • social diagnostics: logs, trackers, API counter, Remotion props, MP4s
  • daily refresh diagnostics: logs, quarantine, API counter, upcoming TGEs, movers OG image
  • daily content diagnostics: logs, quarantine, queue, prices, API counter
  • deploy diagnostics: build output, Next diagnostics, data blobs, registry, sitemap files, npm/build logs
  • performance diagnostics: Lighthouse CI reports

Quality, Security, and Snapshots

.github/workflows/performance.yml protects frontend performance. It builds the static export, runs Lighthouse CI, uploads .lighthouseci/, and runs live PageSpeed snapshots outside pull requests when PAGESPEED_API_KEY is present.

.github/workflows/dependency-security.yml runs npm run audit:prod, which maps to npm audit --omit=dev --audit-level=high.

.github/workflows/monthly-data-snapshot.yml creates a monthly tokenradar-data-YYYY-MM.tar.gz archive plus checksum, then publishes it as data-snapshot-YYYY-MM if that release does not already exist. Runtime caches, logs, quarantine, and social cooldown state are excluded.

Operational Notes

  • CoinGecko usage is managed through src/lib/coingecko.ts, which uses caching plus a monthly quota counter.
  • Queue publication writes into content/tokens/, not a hidden runtime store.
  • Static deployment is performed by GitHub Actions with wrangler pages deploy, not by a separate Cloudflare webhook-only build path.
  • [skip ci] commits from refresh/content workflows avoid duplicate push deploys; those workflows call deploy explicitly when they have changes.
  • Actions cache stores npm/cache data and social cooldown state. Failure diagnostics use Actions artifacts. Monthly long-lived data snapshots use GitHub Releases.
  • Cloudflare Web Analytics can be enabled separately from this automation stack; live PageSpeed snapshots are optional and depend on PAGESPEED_API_KEY.
